# Deploying VyapAI on Render

End-to-end walkthrough for the Docker deploy defined in
[`render.yaml`](../render.yaml) (repo root) / [`../render.yaml`](../render.yaml).

**What you end up with:** a public HTTPS URL serving the API (`/health`), the
merchant dashboard (`/app/`), and the Telegram webhook (`/webhooks/telegram`),
backed by a managed Postgres.

**Cost:** ₹0 on free tiers. Two honest limits, both explained at the bottom:
the free web service sleeps after 15 idle minutes, and the container's disk is
ephemeral.

---

## 0. Prerequisites

- The repo pushed to GitHub (this workspace's remote is
  `github.com/DarshAwasthi2005/VyapAI`).
- Accounts on [render.com](https://render.com) and [neon.com](https://neon.com)
  (both free, no card).

Push any local work first — Render deploys straight from the branch, not from
your laptop:

```bash
git status                      # see what is uncommitted
git add -A && git commit -m "Deploy config for Render"
git push origin main
```

> `.env` is git-ignored, so no local secret is pushed. `.env.example` is
> committed and now holds placeholders only — keep it that way.

## 1. Create the Postgres database (Neon, ~3 min)

Render's own free Postgres is **deleted 30 days after creation**, so use Neon
for anything you want to keep.

1. neon.com → **New Project** → name it `vyapai`.
2. Copy the **connection string**. It looks like:
   ```
   postgresql://neondb_owner:PASSWORD@ep-cool-name-123456.ap-southeast-1.aws.neon.tech/neondb?sslmode=require
   ```
3. Change the scheme to `postgresql+psycopg2://` (this tells SQLAlchemy which
   driver to use — `psycopg2-binary` is already in `requirements.txt`):
   ```
   postgresql+psycopg2://neondb_owner:PASSWORD@ep-cool-name-123456.ap-southeast-1.aws.neon.tech/neondb?sslmode=require
   ```
   Keep `?sslmode=require` — Neon refuses unencrypted connections.

No tables to create by hand: the container runs `alembic upgrade head` on every
boot.

## 2. Create the Render service (~4 min)

1. Render Dashboard → **New → Blueprint**.
2. Pick the `VyapAI` repo. Render finds `render.yaml` at the repository root and
   shows the `vyapai` service (`rootDir: vyapai` means the Dockerfile in this
   folder is used).
3. Click **Apply** / **Create**. Render now asks for the values marked
   `sync: false`:

| Variable | Value |
|---|---|
| `DATABASE_URL` | the Neon string from step 1 (`postgresql+psycopg2://…`) |
| `TELEGRAM_BOT_TOKEN` | token from @BotFather |
| `TELEGRAM_SECRET_TOKEN` | output of `python -c "import secrets; print(secrets.token_urlsafe(32))"` — save it, step 4 needs it too |
| `GROQ_API_KEY` | console.groq.com — voice-note transcription + text structuring |
| `GEMINI_API_KEY` | aistudio.google.com — bill-photo OCR |
| `UPI_PAYEE_VPA` | your UPI ID, e.g. `7619085000@pz` |
| `UPI_PAYEE_NAME` | name shown in the buyer's UPI app |
| `SMTP_USER` / `SMTP_PASSWORD` / `SMTP_FROM` | Gmail address + **App Password** (Google Account → Security → 2-Step Verification → App passwords). `SMTP_FROM` is normally the same address |

`SECRET_KEY` and `WHATSAPP_APP_SECRET` are generated by Render; leave them.

> **Why SMTP matters:** with `APP_ENV=production` the login endpoint refuses to
> hand out a code it cannot deliver (503). Without SMTP there is no way to sign
> in to the dashboard. It deliberately does *not* fall back to showing the code
> on screen — that fallback (`dev_echo`) is development-only because on a public
> URL it would let anyone log in as your shop.

## 3. Verify the deploy

The build takes ~3–5 minutes (pip install). Then:

```bash
curl -s https://<your-service>.onrender.com/health
# {"status":"ok","env":"production"}
```

Open `https://<your-service>.onrender.com/` → the dashboard should load, and
`/docs` shows the API reference.

If the deploy fails, open the service → **Logs**:

| Log | Cause |
|---|---|
| `WHATSAPP_APP_SECRET is not set` | the env var did not get created — add it manually (any random string) |
| `could not translate host name` / `connection refused` | `DATABASE_URL` wrong, or `sslmode=require` missing on Neon |
| `Target database is not up to date` | migrations were interrupted — redeploy (they re-run automatically) |

## 4. Point Telegram at the Render URL

**Stop the local poller first.** `getUpdates` (the local
`scripts/telegram_poller.py`) and a webhook are mutually exclusive — leaving
both running makes Telegram hand updates to only one of them.

```bash
curl -s "https://api.telegram.org/bot<TOKEN>/setWebhook" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://<your-service>.onrender.com/webhooks/telegram",
    "secret_token": "<TELEGRAM_SECRET_TOKEN>",
    "allowed_updates": ["message", "callback_query"]
  }'
# {"ok":true,"result":true,"description":"Webhook was set"}
```

Confirm, then send the bot a message:

```bash
curl -s "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"
```

`last_error_message` should stay empty and `pending_update_count` should fall to
0. (`secret_token` is what makes the endpoint reject anyone else who discovers
the URL — the handler returns 401 without a matching `X-Telegram-Bot-Api-Secret-Token`.)

To go back to local polling later: `curl "https://api.telegram.org/bot<TOKEN>/deleteWebhook"`.

## 5. Set up the shop on the live URL

The Neon database starts empty — the Render deploy does **not** copy your local
`vyapai-dev.db`. On the live dashboard:

1. Register the shop (email login → the OTP arrives by email once SMTP is set).
2. Add the products/prices (the catalog drives availability checks and totals).
3. **Channels → link Telegram** and send `/start <code>` to your bot from the
   shop owner's account, so order cards, verify buttons and payment settlement
   reach the right chat.

If you want the existing local data on the live site instead, that is a separate
migration (`pg_dump`-style copy from SQLite to Postgres) — ask before doing it;
the schemas are identical, but the merchant/product rows must be matched by hand.

## 6. Free-tier limits, honestly

| Limit | Effect | Fix |
|---|---|---|
| Sleeps after 15 min idle (~60 s cold start) | the first request — or the first Telegram message — after a quiet period can time out; Telegram retries deliveries, so messages usually still land | upgrade the service to Starter ($7/mo) for always-on |
| Ephemeral filesystem | voice notes and bill photos (`MEDIA_BACKEND=local`) are lost on redeploy/restart/sleep | set `MEDIA_BACKEND=r2` + the four `R2_*` vars and add `boto3` to `requirements.txt` |
| 750 instance hours/month | a sleeping service uses none; a constantly-woken one can exhaust the pool | upgrade, or keep it idle overnight |
| Free Render Postgres expires in 30 days | data loss | use Neon (this guide) or upgrade the database |

A paid always-on worker could run `python scripts/telegram_poller.py` instead of
a webhook, but on the free plan the webhook is the cheaper and more reliable
choice.

## Local sanity check before deploying (optional)

```bash
cd vyapai
docker build -t vyapai .
docker run --rm -p 8000:8000 --env-file .env vyapai
curl -s localhost:8000/health
```

That exercises the exact image Render builds, including the
`alembic upgrade head && uvicorn …` entrypoint.
